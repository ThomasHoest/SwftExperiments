## Context

Voxio v1.0 uses three interlocked speech-pipeline components: `AVService` (continuous `SFSpeechRecognizer` loop with silence detection), `VoiceToText` (permission gate, locale switching, transcript callbacks), and `CommandParserRouter` (introduced in E-18, currently returning `ParsedCommand`). Voice confirmations are handled by `ConfirmationCoordinator`, which speaks the read-back via `AVSpeechSynthesizer`, shows a `ConfirmationSheet` with Yes/No buttons, and waits for resolution with a 10-second auto-cancel timeout.

v1.1 proposes three changes to this pipeline:

1. **E-24 — Three-Tier Parsing**: Replace the keyword-only `CommandParser` (Tier 3 fallback) with a router that routes each transcript through Foundation Models (Tier 1, A17 Pro+), a retrained `NLModel` (Tier 2, all devices), or the existing keyword parser (Tier 3).
2. **E-25 — Auto-Execute Countdown**: Replace the Yes/No confirmation pattern with a 3-second auto-execute countdown; a single Cancel control is the only user action required.
3. **E-26 — Trigger Word**: Replace the always-on `SFSpeechRecognizer` with a passive/active orb state machine that wakes on "Voxio".

This ADR reviews E-24, E-25, and E-26 only. E-20 through E-23 (visual layer) are covered by ADR-001.

## Decision

Three sets of changes are adopted as specified, subject to the conflicts and clarifications enumerated below.

### Decision 1 — Three-Tier `CommandParserRouter` (E-24)

Extend the existing `CommandParserRouter` to wrap three tiers: Foundation Models `LanguageModelSession` (Tier 1, gated by `SystemLanguageModel.default.availability == .available`), per-language `NLModel` (Tier 2, primary floor for all devices), and the existing `CommandParser` keyword parser (Tier 3, unchanged). The router exposes `func parse(_ transcript: String) async -> VoiceCommand` as its public API.

**Critical clarification required (see Conflict 1):** The current `CommandParserRouter` returns `ParsedCommand`, not `VoiceCommand`. Adopting the proposed API means retiring the entire E-18 `ParsedCommand`-based dispatch path in `HomeView.swift` (lines 454–559) and switching `HomeView.swift` to the existing `VoiceCommand`-based `dispatch(command: VoiceCommand, to: Speaker)` path (lines 365–411). This consolidation is architecturally correct and must be explicitly scoped into E-24's implementation plan.

### Decision 2 — Auto-Execute Countdown via `ConfirmationCoordinator` API Change (E-25)

Replace `ConfirmationCoordinator.request(message:) async -> Bool` with `startCountdown(action:readBack:onResolved:)`. Remove `confirm()` and `cancel()`. Remove the 10-second `Task.sleep` timeout from `ConfirmationCoordinator`. Build `CountdownConfirmationSurface` as the new presentation surface.

### Decision 3 — Wake-Word State Machine (E-26)

Build `TriggerWordDetector` and `TriggerWordController` as the new entry path for speech recognition. Default implementation uses `SFSpeechRecognizer` with `requiresOnDeviceRecognition = true` in continuous mode scanning for "Voxio". Provide a clean callback surface for a lower-power API substitution if T-2603 finds one. The orb gains passive/active states driven by `TriggerWordController.state`.

## Options Considered

### E-24 — Parsing Architecture Alternatives

**Option A (chosen): Three-tier router with availability gate at session start.**
Foundation Models as Tier 1 on A17 Pro+, retrained `NLModel` as Tier 2 floor, existing `CommandParser` as Tier 3. Tier selection computed once at router init; session-level Tier 1 downgrade on three consecutive latency exceedances (>1.5 s per call).

Advantages: on-device, offline, private, bilingual. Tier 2 provides a contractual accuracy floor independent of Tier 1 availability. The existing `CommandParser` means v1.0 canonical phrasings can never regress.

**Option B (rejected): Tier 2 only — retrained `NLModel` as the sole parser.**
Simpler. No Foundation Models dependency. Rejected: leaves performance improvement on the table for A17 Pro+ devices and does not meet the ≥96% accuracy goal.

**Option C (rejected): Cloud NLU (Wit.ai, Dialogflow, OpenAI, Claude, AWS Lex, Azure CLU).**
Eliminated by the non-negotiable on-device privacy NFR.

**Option D (rejected): CoreML transformer (BERT/distilBERT).**
Researcher Rank 3 fallback. Deferred unless Tier 2 NLModel fails ≥92% after two retraining rounds (Q14).

### E-25 — Confirmation Pattern Alternatives

**Option A (chosen): Auto-execute after 3-second countdown, single Cancel control (tap or voice).**
Removes Yes-tap friction. Preserves cancel safety. The inversion from v1.0 (missing decision = cancel) to v1.1 (missing decision = execute) is deliberate and correct for a voice-first app.

**Option B (rejected): Keep Yes/No buttons, shorten timeout to 3 seconds.**
Does not remove the friction; the required confirmation tap for unambiguous commands remains.

**Option C (considered): Confirm-by-voice "yes"/"ja" fires the action early.**
Deferred to Q22. Additive to the countdown; could be introduced in v1.2 without breaking the v1.1 countdown contract.

**Option D (considered): Skip countdown for "safe" intents, longer countdown for destructive intents.**
Deferred to Q21 for v1.2. Uniform 3-second countdown for all confirmable intents in v1.1.

### E-26 — Trigger-Word Implementation Alternatives

**Option A (chosen): `SFSpeechRecognizer` continuous on-device mode scanning partial transcripts for "Voxio".**
Reuses existing `AVService`/`SFSpeechRecognizer` infrastructure. No new frameworks or dependencies. Battery cost is the primary risk; T-2603 investigates a lower-power alternative and T-2610 measures the actual reduction on device.

**Option B (deferred): Dedicated iOS 26 keyword-spotting API.**
Potentially 30%+ more power-efficient. Investigation in T-2603 before T-2606 begins. If found and confirmed, replaces `TriggerWordDetector` internals under the same callback surface — `TriggerWordController` does not need to change.

**Option C (rejected): Third-party wake-word SDK (Picovoice Porcupine, Snowboy, etc.).**
Introduces third-party dependency, custom acoustic model training for "Voxio", and potential telemetry conflicts with the on-device privacy NFR. Escalation path only if Option A fails the battery NFR and Option B is unavailable.

**Option D (rejected): Push-to-talk (tap the orb to activate).**
Eliminates battery concern but breaks the voice-first UX intent. Explicitly out of scope.

## Rationale

**E-24:** Three-tier is the only design that simultaneously satisfies: on-device, offline, bilingual, and materially more accurate than the v1.0 keyword parser. `NLModel` floor guarantees accuracy improvement is device-independent; Foundation Models is additive. Existing `CommandParser` as Tier 3 provides the regression guarantee with zero model changes.

**E-25:** The 3-second auto-execute removes the Yes-tap for unambiguous commands while preserving a visible, accessible cancellation window reachable by touch or voice in both supported languages. The 10-second v1.0 timeout was a safety net for a slow user — the new countdown inverts this: it assumes the action fires and gives the user 3 seconds to intervene. This is the correct posture for a voice-first app controlling audio equipment across a room.

**E-26:** The trigger-word model closes the battery and false-positive problems of always-on speech recognition without requiring hands-on activation. "Voxio" matches the product name and is unlikely to appear in casual speech in either en-US or da-DK. Two visible orb states (passive/active) provide an unambiguous signal. The 5-second safety timeout recovers from stray activations without user action.

## Consequences

### Positive

- Tier 2 `NLModel` provides a contractual accuracy floor (≥92%) on every supported device, independent of Apple Intelligence availability.
- Tier 1 Foundation Models adds 4–6 percentage points of accuracy on A17 Pro+ with no user-visible latency regression (prewarmed session absorbs cold-start cost).
- Three-tier graceful degradation means any single tier failure is invisible to the user; behaviour collapses cleanly to Tier 3 → `.unknown(transcript)`.
- Auto-execute countdown reduces required confirmation taps from one-per-command to zero in the common case.
- Cancel-by-voice allows hands-free cancellation — critical when the app controls a speaker across a room.
- Passive orb state materially reduces foregrounded mic-attributed battery drain (target ≥30%, verified by T-2610).
- Consolidating on `VoiceCommand` as the router's return type (see Conflict 1 resolution) removes the parallel `ParsedCommand` dispatch path from `HomeView.swift` and simplifies the command-dispatch surface area.

### Negative

- E-24 requires training and shipping two `.mlmodel` files (~400 KB combined), a corpus assembly workflow, and a confidence-threshold tuning process. The ML timeline (T-2401 through T-2410) is on the critical path for E-24.
- Foundation Models `@Generable` / `@Guide(.anyOf(...))` is a WWDC25-era beta API whose syntax may change between Xcode 26 beta and GA. This is the highest implementation risk in the release.
- The battery reduction target for E-26 (≥30%) is aspirational until T-2610 runs on physical device. If `SFSpeechRecognizer` continuous mode does not hit the target, T-2603 must find an alternative before ship — a potential schedule risk.
- `TriggerWordController` introduces a new stateful component between `HomeView.swift` and `VoiceToText`. Lifecycle observer ownership must be transferred (see Conflict 4).

### Constraints on Future Work

- Any new confirmation surface must go through `ConfirmationCoordinator.startCountdown(action:readBack:onResolved:)`. The `request(message:)` / `confirm()` / `cancel()` API must not be reintroduced.
- Any new voice input path must go through `TriggerWordController.start()`. Direct calls to `AVService.startRecording()` that bypass the passive/active state machine break the battery NFR and the orb state.
- `NLModel` confidence threshold values (per language) must be committed to the model card and the router source simultaneously.

## Platform Constraint Violations

No hard platform constraint violations exist. The deployment target is already iOS 26; Foundation Models, `NLModel`, and `SFSpeechRecognizer requiresOnDeviceRecognition` are all iOS 26-available APIs.

**Q13 — Foundation Models API stability (HIGH RISK):** The `LanguageModelSession` + `@Generable` + `@Guide(.anyOf(...))` API documented at WWDC25 is subject to change between Xcode 26 beta and Xcode 26 GA. The availability gate (`SystemLanguageModel.default.availability == .available`) ensures any Tier 1 runtime failure is invisible — Tier 2 carries the full load with no functional regression. Action: assign one engineer to monitor Apple's Xcode 26 release notes through the beta cycle. If the API is withdrawn, document the decision and ship with Tier 2 as the maximum tier.

**Q20 — iOS 26 keyword-spotting API (MEDIUM RISK):** Default `TriggerWordDetector` uses `SFSpeechRecognizer` continuous mode. T-2603 must complete before T-2606 begins. If neither Option A nor a native API meets the 30% battery NFR, Option C (third-party SDK) becomes a scope discussion — not a silent deviation.

**Battery NFR (E-26) — aspirational until T-2610:** The ≥30% mic-attributed power reduction target is stated as an NFR but is unvalidated by measurement. It should be treated as an engineering target, not a ship gate, until T-2610 produces a result. If the target is missed with the default implementation, T-2603 may direct adopting a lower-power API; if that is also unavailable, the NFR number should be revised rather than blocking ship on an aspirational target.

## Conflicts

### Conflict 1 — `CommandParserRouter` return type mismatch (E-24 — critical; spec amendment required before T-2415/T-2416)

**Finding:** The existing `CommandParserRouter` is instantiated at `iOS/Voxio/Features/Home/HomeView.swift:9` and called at lines 292–297 with signature `parse(_:addressedSpeaker:allSpeakers:favoriteNames:)` returning `ParsedCommand`. The E-24 spec proposes the public API become `func parse(_ transcript: String) async -> VoiceCommand` — a different return type and parameter set.

Adopting the proposed API has a large but clean downstream consequence: the E-18 `ParsedCommand`-based dispatch section in `HomeView.swift` (functions `confirmationMessage(forParsed:speaker:)`, `completionMessage(forParsed:speaker:)`, and `dispatchParsed(command:to:)`, lines 454–559) becomes obsolete. The existing `VoiceCommand`-based dispatch (`dispatch(command:to:)`, lines 365–411) already covers the same intents with inline slot values in the enum cases (`.playFavorite(index:)`, `.adjustVolume(_:)`, `.setVolume(_:)`). The `onFinalTranscript` handler (line 265) exclusively uses the `ParsedCommand` path today; it must switch to the `VoiceCommand` path.

**Resolution options:**
- **Option A (recommended):** Adopt `VoiceCommand` as the router's return type and retire the `ParsedCommand` dispatch section from `HomeView.swift` in the same PR as T-2415/T-2416. This is a clean unification with no loss of intent expressiveness.
- **Option B (not recommended):** Keep `ParsedCommand` as the router's return type and have the three-tier NLU path emit `ParsedCommand`. This preserves E-18 dispatch code at the cost of forcing the `@Generable IntentResult` type (T-2412) to map to `ParsedCommand` instead of `VoiceCommand` — added complexity with no benefit.

**Required spec amendment:** T-2415 and T-2416 descriptions must explicitly state: (a) the new router returns `VoiceCommand`, (b) the call site at `HomeView.swift:292–297` is updated to use the new async `VoiceCommand`-returning API, and (c) the `ParsedCommand` dispatch section (`HomeView.swift:454–559`) is removed in the same commit.

### Conflict 2 — `VoiceToText.swift:50` is not the authoritative parse call site (E-24 — informational; affects T-2416 scoping)

**Finding:** The spec (Technical Context table and T-2416 description) refers to "the parsing call site in `VoiceToText.swift:50`" as the location to update. However, `VoiceToText.swift:50` executes `CommandParser(language: lang).parse(text)` and fires `self?.onCommand?(command)` — but `HomeView.swift` does **not** subscribe to `voiceToText.onCommand`. The actual command routing happens at `HomeView.swift:292–297` via `commandRouter`, wired from `voiceToText.onFinalTranscript` at `HomeView.swift:265`. The parse at `VoiceToText.swift:50` is dead code with respect to the active dispatch path.

**Required action:** T-2416 should remove the synchronous parse at `VoiceToText.swift:50` (dead code) rather than making it async-aware. The authoritative async parse call site is `HomeView.swift:292–297`. T-2416's description should be corrected accordingly.

### Conflict 3 — All callers of `ConfirmationCoordinator.confirm()` and `.cancel()` (E-25 — moderate; blocks T-2501/T-2508)

**Finding:** The current `ConfirmationCoordinator` exposes `confirm()` and `cancel()` (confirmed from `iOS/Voxio/Core/ConfirmationCoordinator.swift:53,58`). These are called at four locations in `HomeView.swift`:

- Line 103: `coordinator.cancel()` inside the sheet-dismiss `Binding.set` closure
- Line 109: `coordinator.cancel()` (labeled `onCancel` in the sheet callback)
- Line 272: `coordinator.confirm()` when voice "yes" is detected while coordinator is pending
- Line 273: `coordinator.cancel()` when voice "no" is detected while coordinator is pending

The entire `ConfirmationSheet` presentation block at `HomeView.swift:101–112` must also be removed.

**Required action:** T-2508 ("Remove the v1.0 `ConfirmationSheet`…") must enumerate all four `confirm()`/`cancel()` call sites and the sheet presentation modifier. The voice-confirm/cancel handler at lines 270–276 must be replaced by `CancelGrammar.swift` (T-2506) logic that operates during the countdown phase only.

### Conflict 4 — Foreground/background lifecycle observer ownership (E-26 — moderate; affects T-2602 design)

**Finding:** `VoiceToText.swift:68–84` installs `UIApplication.didEnterBackgroundNotification` and `UIApplication.willEnterForegroundNotification` observers that call `recorder.stopRecording()` and `recorder.startRecording()` respectively. When `TriggerWordController` takes over the pipeline entry point, a foreground-resume must enter **passive** state (not active state as the current observer does at line 83 by calling `recorder.startRecording()` directly).

**Required action:** T-2602 (`TriggerWordController`) must specify that on foreground-resume, `TriggerWordController.start()` is called (entering passive state). The existing `willEnterForegroundNotification` observer in `VoiceToText.swift:80–85` must be removed or refactored to delegate foreground-resume to the controller. The spec's resolved decision preserving T-0312 background-pause behaviour is correct — only the "resume" path needs updating, not the "background" path.

## Summary Verdict

**PROCEED — with Conflict 1 requiring a spec amendment before T-2415 and T-2416 begin.**

No iOS platform constraint violations exist. All three epics (E-24, E-25, E-26) are architecturally implementable within the iOS 26 deployment target using existing frameworks. Conflict 1 is the only conflict that will produce an incorrect implementation if unresolved — the spec must explicitly state that E-24 retires the `ParsedCommand` dispatch path and that the authoritative parse call site is `HomeView.swift:292–297`, not `VoiceToText.swift:50`. Conflicts 2, 3, and 4 are resolvable during implementation with the guidance in this document.

**Recommended first action for E-24 implementer:** Confirm with the spec owner that `VoiceCommand` is the intended return type for the new router API, then remove the `ParsedCommand` dispatch section from `HomeView.swift` in the same PR as T-2415/T-2416.

**Recommended first action for E-25 implementer:** Enumerate and remove all four call sites of `confirm()` / `cancel()` (`HomeView.swift:103, 109, 272, 273`) and the entire `ConfirmationSheet` presentation block (`HomeView.swift:101–112`) as part of T-2508.

**Recommended first action for E-26 implementer:** Remove the `willEnterForegroundNotification` observer from `VoiceToText.swift:80–85` as part of T-2602, and replace it with a call to `triggerWordController.start()` in the foreground-resume hook in `HomeView.swift` or `VoxioApp.swift`.
