# ADR-002 — Voxio v1.1 Parsing, Confirmation, and Trigger Word

**Status:** Proposed
**Date:** 2026-04-29
**Author:** Architect (voxio-1.1-parsing team)
**Applies to:** iOS platform only (`iOS/Voxio/`)
**References:** VoxioSpecification-1.1.md §1.1.2–1.1.3, epics-and-tasks-voxio-1.1.md (E-24, E-25, E-26), ADR-001-v1.1-visual-layer.md, CLAUDE.md

## Context

Voxio v1.0 ships three interlocked speech-pipeline components: `AVService` (continuous `SFSpeechRecognizer` loop with silence detection at `silenceThreshold = 0.01` / `silenceDuration = 1.5 s`), `VoiceToText` (permission gate, locale switching, transcript callbacks), and `CommandParserRouter` (introduced in E-18, currently returning `ParsedCommand` with a context-rich signature). Voice confirmations are handled by `ConfirmationCoordinator`, which speaks the read-back via `AVSpeechSynthesizer`, shows a `ConfirmationSheet` with Yes/No buttons, and awaits resolution with a 10-second auto-cancel timeout (`Task.sleep(for: .seconds(10))`).

v1.1 proposes three changes to this pipeline:

1. **E-24 — Three-Tier Parsing**: Route each finalised transcript through Foundation Models `LanguageModelSession` (Tier 1, A17 Pro+ with Apple Intelligence), a retrained per-language `NLModel` (Tier 2, all devices — primary floor), and the existing keyword `CommandParser` (Tier 3, unchanged safety net).
2. **E-25 — Auto-Execute Countdown**: Replace the Yes/No sheet with a 3-second auto-execute countdown. A single Cancel control (tap or voice) is the only user action required to stop the action.
3. **E-26 — Trigger Word**: Replace the always-on `SFSpeechRecognizer` with a passive/active orb state machine that wakes on the word "Voxio".

This ADR covers E-24, E-25, and E-26 only. E-20 through E-23 (visual layer) are covered by ADR-001.

**Source files inspected for this review:**
- `iOS/Voxio/Core/Voice/VoiceToText.swift`
- `iOS/Voxio/Core/Voice/AVService.swift`
- `iOS/Voxio/Core/ConfirmationCoordinator.swift`
- `iOS/Voxio/Features/Home/HomeView.swift`

## Decision

All three epics are adopted as specified. Three decisions are recorded below, subject to the four conflicts enumerated in the Conflicts section.

### Decision 1 — Three-Tier `CommandParserRouter` (E-24)

Extend the existing `CommandParserRouter` to wrap three tiers behind a single async API: `func parse(_ transcript: String) async -> VoiceCommand`. Tier 1 uses Foundation Models `LanguageModelSession` gated by `SystemLanguageModel.default.availability == .available`. Tier 2 uses a per-language retrained `NLModel` and is the contractual primary floor for all supported devices. Tier 3 is the existing keyword `CommandParser`, unchanged, as a deterministic safety net. Tier selection is computed once at router init.

Adopting `VoiceCommand` as the return type requires retiring the current E-18 `ParsedCommand`-based dispatch section in `HomeView.swift` (lines 454–559) and activating the existing `VoiceCommand`-based `dispatch(command:to:)` path (lines 365–411). This is the correct consolidation direction (see Conflict 1).

### Decision 2 — Auto-Execute Countdown via `ConfirmationCoordinator` API Replacement (E-25)

Replace `ConfirmationCoordinator.request(message:) async -> Bool`, `confirm()`, and `cancel()` with `startCountdown(action:readBack:onResolved:)` and `cancelCountdown(reason:)`. Remove the 10-second `Task.sleep` timeout. Build `CountdownConfirmationSurface` as the new presentation surface presenting a localised "Cancelling in 3… 2… 1…" label and a single `DarkGlassButton(role: .cancel)`.

### Decision 3 — Wake-Word State Machine (E-26)

Build `TriggerWordDetector` and `TriggerWordController`. The default `TriggerWordDetector` implementation uses `SFSpeechRecognizer` with `requiresOnDeviceRecognition = true` in continuous mode, scanning partial transcripts for whole-word "Voxio" (case-insensitive). `TriggerWordController` owns the passive/active state machine and the 5-second silence safety timeout. The orb renders two distinct states driven by `TriggerWordController.state`. If T-2603 finds a lower-power iOS 26 keyword-spotting API that is ≥30% more efficient, it replaces the `TriggerWordDetector` internals under the same callback surface without changing the controller.

## Options Considered

### E-24 — Parsing Architecture

**Option A (chosen): Three-tier router, availability-gated at session start.**
Foundation Models on A17 Pro+, retrained `NLModel` as the device-universal floor, existing `CommandParser` as safety net. Tier selection at init; session-level Tier 1 downgrade after three consecutive calls exceeding 1.5 s.

Satisfies all four constraints simultaneously: on-device, offline, bilingual, and materially more accurate than the v1.0 keyword parser. The `NLModel` floor guarantees that accuracy improvement is device-independent. The existing `CommandParser` as Tier 3 means v1.0 canonical phrasings can never regress regardless of model quality.

**Option B (rejected): Tier 2 `NLModel` only.**
Simpler, no Foundation Models dependency. Rejected: leaves 4–6 percentage points of accuracy on the table for A17 Pro+ devices and does not reach the ≥96% accuracy goal.

**Option C (rejected): Cloud NLU (Wit.ai, Dialogflow, OpenAI, Claude, AWS Lex, Azure CLU).**
Eliminated by the non-negotiable on-device privacy NFR. No transcript may leave the device.

**Option D (rejected): CoreML transformer (BERT/distilBERT).**
Researcher Rank 3 fallback. Deferred unless Tier 2 `NLModel` fails to reach ≥92% validation accuracy after two retraining rounds (Q14).

### E-25 — Confirmation Pattern

**Option A (chosen): Auto-execute after 3-second countdown, single Cancel control (tap or voice).**
Removes the Yes-tap friction observed in v1.0 field use while preserving a visible, accessible cancellation window. The inversion from v1.0 (missing decision = cancel) to v1.1 (missing decision = execute) is deliberate and correct for a voice-first app controlling audio equipment across a room.

**Option B (rejected): Keep Yes/No buttons, shorten timeout to 3 seconds.**
Does not remove the core friction: an explicit tap is still required for every unambiguous command.

**Option C (considered): Confirm-by-voice "yes"/"ja" fires the action early.**
Deferred to Q22. Could be added in v1.2 as an additive extension to the countdown without breaking the v1.1 contract.

**Option D (considered): Per-intent countdown duration (shorter for safe intents, longer for destructive).**
Deferred to Q21 for v1.2. Uniform 3-second countdown for all confirmable intents in v1.1.

### E-26 — Trigger-Word Implementation

**Option A (chosen): `SFSpeechRecognizer` continuous on-device mode.**
Reuses existing infrastructure. No new frameworks or entitlements. Battery cost is the primary risk; T-2603 investigates a lower-power alternative and T-2610 measures the actual reduction on physical device.

**Option B (deferred): Dedicated iOS 26 keyword-spotting API (Q20).**
Potentially ≥30% more power-efficient than Option A. T-2603 investigates before T-2606 begins. If confirmed, replaces `TriggerWordDetector` internals under the same callback surface — `TriggerWordController` does not change.

**Option C (rejected): Third-party wake-word SDK (Picovoice Porcupine, etc.).**
Third-party dependency, custom "Voxio" acoustic model training required, potential telemetry conflicts with the on-device privacy NFR. Escalation path only if Options A and B both fail the battery NFR.

**Option D (rejected): Push-to-talk (tap the orb to activate).**
Eliminates battery concern but breaks the voice-first UX intent. Explicitly out of scope per the spec.

## Rationale

**E-24:** Three-tier is the only design that simultaneously satisfies all four constraints: on-device, offline, bilingual, and materially more accurate than v1.0. `NLModel` provides a device-universal accuracy floor; Foundation Models adds precision on capable devices. The existing `CommandParser` as Tier 3 ensures the v1.0 regression test suite passes at 100% with zero model changes.

**E-25:** The 3-second auto-execute removes the Yes-tap for unambiguous commands (the dominant case in field use) while preserving a 3-second cancellation window accessible by touch or voice in both languages. The 10-second v1.0 timeout treated missing input as a cancel signal — the new countdown inverts this and fires the action on silence. This inversion is correct: in a voice-first interface controlling a speaker, "I said it and didn't stop it" should equal "do it."

**E-26:** The trigger-word model closes the battery and false-positive problems of the always-on recogniser without requiring hands-on interaction. "Voxio" is phonetically stable in both en-US and da-DK and is unlikely to occur in casual speech. Two visible orb states (passive slow-pulse / active full-amplitude) make the listening boundary explicit and visible. The 5-second safety timeout recovers from stray activations without any user action.

## Consequences

### Positive

- Tier 2 `NLModel` provides a ≥92% accuracy floor on every supported device, independent of Apple Intelligence availability.
- Tier 1 Foundation Models adds 4–6 percentage points on A17 Pro+ with no user-visible latency regression (prewarmed session eliminates cold-start).
- Three-tier graceful degradation: any single-tier failure is invisible; behaviour collapses cleanly to Tier 3 → `.unknown(transcript)`.
- Auto-execute countdown reduces required confirmation taps from one-per-command to zero in the common case.
- Cancel-by-voice preserves hands-free operation and bilingual symmetry.
- Passive orb state targets ≥30% reduction in mic-attributed battery drain versus v1.0 (verified by T-2610).
- Consolidating on `VoiceCommand` as the router return type (Conflict 1 resolution) removes the parallel `ParsedCommand` dispatch section from `HomeView.swift`, simplifying the command-dispatch surface area by ~100 lines.

### Negative

- E-24 requires ML engineering work before the feature can ship: corpus assembly, two `NLModel` training runs (~400 KB combined), confidence threshold calibration. The ML timeline (T-2401–T-2410) is on the critical path.
- Foundation Models `@Generable` / `@Guide(.anyOf(...))` is a WWDC25-era beta API; its syntax may change between Xcode 26 beta and GA. Highest implementation risk in the release.
- The ≥30% battery reduction target (E-26) is aspirational and unvalidated until T-2610 runs on physical hardware. If the default `SFSpeechRecognizer` implementation falls short, T-2603 must find an alternative before ship — a potential schedule risk.
- `TriggerWordController` adds a new stateful component in the speech pipeline. Lifecycle observer ownership must be explicitly transferred from `VoiceToText.swift` (see Conflict 4).

### Constraints on Future Work

- Any new confirmation surface must route through `ConfirmationCoordinator.startCountdown(action:readBack:onResolved:)`. The `request(message:)` / `confirm()` / `cancel()` API must not be reintroduced.
- Any new voice input path must enter through `TriggerWordController.start()`. Direct calls to `AVService.startRecording()` that bypass the passive/active state machine break both the battery NFR and the orb state.
- `NLModel` per-language confidence thresholds must be committed to the model card and to the router source in the same PR.

## Platform Constraint Violations

No hard platform constraint violations exist. The deployment target is already iOS 26. Foundation Models, `NLModel`, and `SFSpeechRecognizer` with `requiresOnDeviceRecognition` are all available on iOS 26.

The following risks are flagged:

**Q13 — Foundation Models API stability (HIGH RISK).** The `LanguageModelSession` + `@Generable` + `@Guide(.anyOf(...))` API documented at WWDC25 is subject to change between Xcode 26 beta and GA. The availability gate (`SystemLanguageModel.default.availability == .available`) ensures any Tier 1 failure is invisible at runtime — Tier 2 carries the full load. **Action:** one engineer monitors Apple's Xcode 26 release notes through the beta cycle. If the API is withdrawn, document the decision and ship with Tier 2 as the maximum tier; no user-visible regression results.

**Q20 — iOS 26 keyword-spotting API (MEDIUM RISK).** The default `TriggerWordDetector` uses `SFSpeechRecognizer` continuous mode. T-2603 must complete before T-2606 begins. If neither Option A nor a native API meets the 30% battery NFR, Option C (third-party SDK) becomes a scope discussion — not a silent deviation.

**Battery NFR (E-26) — aspirational until T-2610.** The ≥30% mic-attributed power reduction is an engineering target, not a measured result. It must not block ship if the target is missed by a small margin after T-2603 has been exhausted; the NFR number should be revised in that case rather than holding the release.

## Conflicts

### Conflict 1 — `CommandParserRouter` return type mismatch (E-24 — critical; spec amendment required before T-2415/T-2416)

**Finding.** `HomeView.swift:9` instantiates `CommandParserRouter` and calls it at lines 292–297 with the signature:

```swift
let command = await commandRouter.parse(
    commandText,
    addressedSpeaker: speaker,
    allSpeakers:      registry.speakers.map(\.name),
    favoriteNames:    favoriteNames
)
```

This returns a `ParsedCommand`. The E-24 spec proposes replacing the public API with `func parse(_ transcript: String) async -> VoiceCommand` — a different return type and a simpler parameter set.

Adopting the proposed API has a large but clean downstream consequence. The entire E-18 `ParsedCommand`-based section in `HomeView.swift` — `confirmationMessage(forParsed:speaker:)`, `completionMessage(forParsed:speaker:)`, and `dispatchParsed(command:to:)` at lines 454–559 — becomes obsolete. The existing `VoiceCommand`-based `dispatch(command:to:)` at lines 365–411 already covers the same intents with slots carried directly in enum cases (`.playFavorite(index:)`, `.adjustVolume(_:)`, `.setVolume(_:)`). The `onFinalTranscript` handler at line 265 currently uses only the `ParsedCommand` path and must switch to the `VoiceCommand` path.

**Resolution (recommended — Option A):** Adopt `VoiceCommand` as the new router return type and retire the `ParsedCommand` dispatch section from `HomeView.swift` in the same PR as T-2415/T-2416. This is a clean unification with no loss of intent expressiveness.

**Required spec amendment.** T-2415 and T-2416 descriptions must explicitly state: (a) the new router returns `VoiceCommand`; (b) the call site at `HomeView.swift:292–297` is updated to use the new async API; and (c) the `ParsedCommand` dispatch section (`HomeView.swift:454–559`) is removed in the same commit.

### Conflict 2 — `VoiceToText.swift:50` is not the authoritative parse call site (E-24 — informational; affects T-2416 scoping)

**Finding.** The spec Technical Context table and T-2416 description both refer to "the parsing call site in `VoiceToText.swift:50`" as the location to update. However, `VoiceToText.swift:50` executes `CommandParser(language: lang).parse(text)` and fires `self?.onCommand?(command)` — and `HomeView.swift` does **not** subscribe to `voiceToText.onCommand`. The active command routing path is `HomeView.swift:292–297` via `commandRouter`, wired from `voiceToText.onFinalTranscript` at `HomeView.swift:265`. The parse at `VoiceToText.swift:50` is dead code with respect to the current dispatch path.

**Required action.** T-2416 should remove the synchronous parse at `VoiceToText.swift:50` (it is dead code) rather than making it async-aware. The authoritative async parse call site is `HomeView.swift:292–297`. T-2416's description should be corrected to reflect this.

### Conflict 3 — All callers of `ConfirmationCoordinator.confirm()` and `.cancel()` (E-25 — moderate; must be enumerated in T-2508)

**Finding.** `ConfirmationCoordinator` currently exposes `confirm()` (line 53) and `cancel()` (line 58), both confirmed from `iOS/Voxio/Core/ConfirmationCoordinator.swift`. These are called at four distinct locations in `HomeView.swift`:

- **Line 103:** `coordinator.cancel()` — inside the sheet-dismiss `Binding.set` closure
- **Line 108:** `coordinator.confirm()` — as the `onConfirm` callback wired to `ConfirmationSheet`
- **Line 109:** `coordinator.cancel()` — as the `onCancel` callback wired to `ConfirmationSheet`
- **Line 272:** `coordinator.confirm()` — voice "yes" detected while coordinator is pending
- **Line 273:** `coordinator.cancel()` — voice "no"/"cancel" detected while coordinator is pending

The entire `ConfirmationSheet` presentation block at `HomeView.swift:101–112` (the `.sheet(isPresented: Binding(get: { coordinator.isPending }, ...))` modifier and its content) must also be removed.

The voice-confirm/cancel handler at `HomeView.swift:270–276` (which calls `CommandParser` directly to detect `.confirm` / `.cancel` while the coordinator is pending) is replaced by the `CancelGrammar.swift` (T-2506) keyword detector, which operates during the countdown phase only.

**Required action.** T-2508 ("Remove the v1.0 `ConfirmationSheet`…") must enumerate all five `confirm()`/`cancel()` call sites and the sheet presentation block at lines 101–112.

### Conflict 4 — Foreground/background lifecycle observer ownership (E-26 — moderate; must be resolved in T-2602)

**Finding.** `VoiceToText.swift:68–84` installs two `NotificationCenter` observers inside `start()`:

- `UIApplication.didEnterBackgroundNotification` (line 68–75): calls `recorder.stopRecording()`
- `UIApplication.willEnterForegroundNotification` (line 77–85): calls `try? self?.recorder.startRecording()` — entering **active** recording state directly

When `TriggerWordController` takes over the pipeline entry point, a foreground-resume must enter **passive** state (low-cost "Voxio" scanning), not active full-recognition state. The existing `willEnterForegroundNotification` handler bypasses the controller and would re-enter active state on every foreground return.

**Required action.** As part of T-2602, the `willEnterForegroundNotification` observer in `VoiceToText.swift:78–85` must be removed. Foreground-resume must be re-wired to call `triggerWordController.start()` (which enters passive state) from the appropriate hook in `HomeView.swift` or `VoxioApp.swift`. The `didEnterBackgroundNotification` observer (stop recording) is correct and should be preserved, consistent with the spec's resolved decision to keep T-0312 background-pause behaviour.

## Implementation Notes

### E-24 call-site migration in `HomeView.swift`

The `onFinalTranscript` handler at `HomeView.swift:265–322` currently does:
1. Speaker resolution (`registry.resolve(words:)`) — unchanged
2. Calls `commandRouter.parse(commandText, addressedSpeaker:allSpeakers:favoriteNames:)` → `ParsedCommand`
3. Calls `confirmationMessage(forParsed:speaker:)` → confirmation message string
4. Calls `coordinator.request(message:)` → `Bool`
5. Calls `dispatchParsed(command:to:)` → `Bool`

After E-24 + E-25:
1. Speaker resolution — unchanged
2. Calls `commandRouter.parse(commandText)` → `VoiceCommand`
3. Calls `confirmationMessage(for:speaker:)` (the `VoiceCommand` overload at line 330) → confirmation string
4. Calls `coordinator.startCountdown(action:readBack:onResolved:)` — no `await Bool` return
5. The bound action closure calls `dispatch(command:to:)` (the `VoiceCommand` overload at line 365)

The E-18 `ParsedCommand` section (lines 454–559) is removed in the same commit.

### E-26 state machine integration

`TriggerWordController.start()` is called from `HomeView.startListening()` (currently line 243) instead of — or immediately before — `voiceToText.start(onStatus:)`. The controller takes over the foreground/background lifecycle observer responsibility from `VoiceToText.swift`. The `TriggerWordController` callback that fires on trigger detection hands control to the existing `AVService`-backed full recognition pipeline for the active phase; silence detection and final-transcript delivery remain in `AVService`/`VoiceToText` unchanged.

---

## Summary Verdict

**PROCEED — with Conflict 1 requiring a spec amendment before T-2415 and T-2416 begin.**

No iOS platform constraint violations exist. All three epics are implementable within the iOS 26 deployment target using existing frameworks. Conflict 1 is the only issue that will produce an incorrect implementation if unresolved: the spec must explicitly state that the new router returns `VoiceCommand`, that the call site is `HomeView.swift:292–297`, and that the `ParsedCommand` dispatch section at lines 454–559 is removed in the same PR. Conflicts 2, 3, and 4 are all resolvable during implementation using the guidance in the Conflicts section above.

**Recommended first actions:**

- **E-24 implementer:** Confirm `VoiceCommand` is the intended router return type, then retire `HomeView.swift:454–559` in the same PR as T-2415/T-2416.
- **E-25 implementer:** Remove all five `confirm()`/`cancel()` call sites (`HomeView.swift:103, 108, 109, 272, 273`) and the `ConfirmationSheet` presentation block (`HomeView.swift:101–112`) as part of T-2508.
- **E-26 implementer:** Remove the `willEnterForegroundNotification` observer from `VoiceToText.swift:78–85` as part of T-2602 and re-wire foreground-resume to `triggerWordController.start()`.
