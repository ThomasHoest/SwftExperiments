# ADR-001 — Voxio v1.1 Visual Layer Architecture

**Status:** Proposed
**Date:** 2026-04-29
**Author:** Architect (voxio-1.1 team)
**Applies to:** iOS platform only (`iOS/Voxio/`)
**References:** VoxioSpecification-1.1.md, design-spec-bo-voice-control v1.1

---

## Context

Voxio v1.0 ships a functional voice-controlled B&O speaker interface. The visual layer has three inconsistencies that v1.1 corrects:

1. **Background:** `HomeView` renders a dark-charcoal `LinearGradient` (`#0D0D14` → `#151520`). The v1.0 plan to use the user's iOS wallpaper through a glass layer (T-1001) was never implemented; the gradient is the current shipped state. v1.1 replaces both with a fixed `AppBackground.png` asset.

2. **Button rendering:** Three different button styles exist across three screens, none of which matches the v1.1 design intent:
   - `ConfirmationSheet` Yes button: solid gold `RoundedRectangle(cornerRadius: 12)` fill with dark `#0D0D14` text (no glass).
   - `ConfirmationSheet` No button: `.glassEffect(in: RoundedRectangle(cornerRadius: 12))` with a 1 pt white stroke.
   - `LanguagePickerSheet` English button: identical to the Yes button above.
   - `LanguagePickerSheet` Danish button: identical to the No button above.
   - `HintCardView` dismiss button: `.glassEffect(in: RoundedRectangle(cornerRadius: Radius.sheet))` with a 1 pt white stroke.
   - `HomeView` hint toggle button: raw `Button` wrapping an `Image(systemName:)` — no glass surface.
   None of these are capsule-shaped. v1.1 unifies all to a single reusable `DarkGlassButton` using `Capsule()` geometry.

3. **Sheet dark-mode enforcement:** `VoxioApp.swift` applies `.preferredColorScheme(.dark)` at the `WindowGroup` level. Neither `LanguagePickerSheet` nor `ConfirmationSheet` applies the modifier to their own content root. On a light-mode system device, both sheets render in light mode — a visible regression against the dark-only design intent.

4. **Increase Contrast path:** No references to `UIAccessibility.isContrastEnabled` were found in `iOS/Voxio/`. The contrast-reactive border treatment specified in v1.1 does not exist yet — it must be built using `@Environment(\.colorSchemeContrast)`. This is additive work, not a replacement.

The iOS 26 `.glassEffect` API is already in use throughout the codebase: `SpeakerCard`, `ConnectionStatusChip`, `SpeakerSelectorPill`, `ConfirmationSheet` No button, `HintCardView` dismiss button, and the success toast all call `.glassEffect(in:)`. The deployment target is already iOS 26. No new platform capability is required by v1.1.

---

## Decision

Three changes are adopted exactly as specified:

### Decision 1 — Replace gradient background with `AppBackground.png`

Replace the `LinearGradient` in `HomeView.background` with `Image("AppBackground").resizable().scaledToFill().ignoresSafeArea()` as the first child of the root `ZStack`. Add an `appBackground` string constant to `DesignTokens.swift`. Provide a `Color(hex: "#0A0E1A")` fallback via `UIImage(named:)` precheck at view init.

The `ZStack` structure in `HomeView` is already correct for this — `background` is placed first and `VStack` content follows. The `.ignoresSafeArea()` is already on the background only, not the `ZStack`, which is the required idiom.

### Decision 2 — Build `DarkGlassButton` and replace all ad-hoc buttons

Build a single `DarkGlassButton` SwiftUI view in `iOS/Voxio/DesignSystem/DarkGlassButton.swift` using `.glassEffect(.regular.tint(.black.opacity(0.45)).interactive(), in: Capsule())` with a `Capsule().strokeBorder(Color.white.opacity(0.15), lineWidth: 0.5)` overlay. Add a `DarkGlassIconButton` icon-only variant (36 × 36 pt visual, 44 × 44 pt hit area via `.frame(minWidth: 44, minHeight: 44)`).

Replace all five existing ad-hoc button surfaces: both buttons in `ConfirmationSheet`, both buttons in `LanguagePickerSheet`, the dismiss button in `HintCardView`, and the hint-toggle in `HomeView.statusBar`. The `SpeakerSelectorPill` is explicitly excluded (it is a selection control with an active/inactive gold tint state, not a command button).

Add `DarkGlassButton` namespace tokens to `DesignTokens.swift`.

### Decision 3 — Enforce dark mode at every sheet presentation boundary

Add `.preferredColorScheme(.dark)` to the `body` root of `LanguagePickerSheet` and `ConfirmationSheet`. Document the requirement in a header comment or `DesignSystem/README.md` so future sheet authors know the rule. Add `@Environment(\.colorSchemeContrast)` reactive border treatment to `DarkGlassButton`, `DarkGlassIconButton`, and `SpeakerCard`.

## Options Considered

### Decision 1 — Background alternatives

**Option A (chosen):** `Image("AppBackground").resizable().scaledToFill().ignoresSafeArea()`.
Simple, zero-overhead, matches existing `ZStack` structure, no new dependencies.

**Option B:** Keep gradient, use `UIVisualEffectView` tinted overlay to simulate depth.
Rejected: does not match the design spec's fixed orb image. The orb is a deliberate B&O brand element, not achievable with a gradient + tint.

**Option C:** Render the user's iOS wallpaper through a glass layer (original T-1001 intent).
Rejected by design v1.1 explicitly: wallpaper-adaptive rendering violates the brand-controlled canvas intent. Also introduces `UIWallpaper` private API risk on iOS 26.

### Decision 2 — Button system alternatives

**Option A (chosen):** Single `DarkGlassButton` reusable view with a `Role` enum, placed in `DesignSystem/`.
Matches existing `BeoColor` / `DesignTokens` organisation. One file to audit, one place to apply contrast changes, one place to update if the iOS API changes.

**Option B:** Keep per-screen button styling, apply dark glass to each call site individually.
Rejected: three screens currently have divergent implementations. The spec exists precisely to unify them. Per-site application guarantees drift over time — any new sheet would require knowing to replicate the pattern.

**Option C:** Use a SwiftUI `ButtonStyle` instead of a wrapper view.
Considered but rejected for icon/label composition: `ButtonStyle` does not have access to the button content for inserting the SF Symbol with role-specific tinting without breaking the label hierarchy. A wrapper view is cleaner for the `HStack { icon; label }` pattern with role-conditional colours.

### Decision 3 — Dark mode enforcement alternatives

**Option A (chosen):** Per-sheet-body `.preferredColorScheme(.dark)` modifier.
The idiomatic SwiftUI approach. Each presentation boundary is self-contained. No UIKit shim required. Zero risk of breaking other views.

**Option B:** `window.overrideUserInterfaceStyle = .dark` via `UIWindowSceneDelegate`.
Would also dark-mode system-rendered permission alerts (microphone, speech, local network). The spec explicitly accepts these as out of scope. Adding a UIKit shim for a behaviour not required by the spec introduces UIKit coupling without benefit, and `overrideUserInterfaceStyle` on a `UIWindow` is not a public-API-stable approach on iOS 26 where scene-based window management has changed.

**Option C:** Apply `.environment(\.colorScheme, .dark)` instead of `.preferredColorScheme(.dark)`.
`.environment` overrides the environment value but does not propagate the preference up to the host; `.preferredColorScheme` is the correct modifier for this use case. Using `.environment` risks some system-rendered chrome (e.g. sheet drag handle, safe area background) not honouring the override.

## Consequences

### Positive

- A single `DarkGlassButton` component eliminates three independent implementations that diverged during v1.0.
- `@Environment(\.colorSchemeContrast)` in `DarkGlassButton` means any future button call site gets reactive contrast handling for free, with no observer registration required.
- The fixed background is a `ZStack` first-child swap — lowest risk change in the release; no layout recalculation required.
- Sheet dark-mode enforcement is a one-line modifier per sheet. If a new sheet is added, the rule is documented and discoverable.
- No new dependencies, no new frameworks, no new entitlements.

### Negative

- `DarkGlassButton` uses `Capsule()` geometry; all current ad-hoc buttons use `RoundedRectangle(cornerRadius: 12)`. This is a visible shape change in `ConfirmationSheet` and `LanguagePickerSheet` — the buttons will appear more pill-like. The design spec intends this. Verify against the `ButtonLookAndFeel.png` reference before shipping.
- `scaledToFill` on `AppBackground.png` will crop the image horizontally on iPhone SE (375 pt) vs Pro Max (430 pt). The design team must confirm the orb composition tolerates ~5–10% horizontal crop (open question Q9 in the spec).
- Snapshot test infrastructure (`swift-snapshot-testing` or similar) must be added if not already present. E-23 has nine snapshot-dependent tasks that will block on this tooling decision (open question Q8 in the spec).
- `DarkGlassButton` adds a new file and a new tokens namespace. Small maintenance surface increase.

### Constraints on future work

- Any new `.sheet`, `.fullScreenCover`, or `.popover` content view must apply `.preferredColorScheme(.dark)` to its body root. Document this as a project convention.
- The `SpeakerSelectorPill` is intentionally excluded from `DarkGlassButton`. If a future release decides to migrate the selector pill, the T-2110 exception comment must be removed and the component rebuilt.
- The `appBackground` token references an `Assets.xcassets` imageset by string name. If the asset is renamed, the token constant must be updated. Keep the token constant as the only call site for the string.

## Implementation Notes

### Background swap (E-20)

- `HomeView.background` is a computed property returning `LinearGradient(...).ignoresSafeArea()`. Replace the body of this computed property with the image. Do not move `.ignoresSafeArea()` to the `ZStack` — moving it would cause all `ZStack` children to ignore the safe area.
- The fallback precheck pattern: `if UIImage(named: "AppBackground") == nil { show Color(hex: "#0A0E1A") }`. This runs synchronously at view init and adds no async overhead.
- Do not use `@1x / @2x / @3x` in code — Xcode asset catalogs resolve the correct scale automatically from `UIImage(named:)` and `Image(_:)`.

### `DarkGlassButton` (E-21)

- Use `.glassEffect(.regular.tint(.black.opacity(0.45)).interactive(), in: Capsule())`, not `.glassEffect(in: Capsule())`. The `.tint` and `.interactive()` modifiers are required by the spec. The plain `.glassEffect(in:)` used on the toast and emptyState is intentionally lighter.
- Use `Capsule().strokeBorder(Color.white.opacity(0.15), lineWidth: 0.5)` inside `.overlay(...)`. `strokeBorder` (not `stroke`) keeps the hairline entirely inside the clip boundary. Using `stroke` would cause the hairline to straddle the capsule edge and bleed visually.
- The `ButtonStyle` press animation: `scaleEffect(0.95)` with `.spring(response: 0.3, dampingFraction: 0.7)`. These spring parameters differ from the global `BeoAnimation.spring` (response 0.45, damping 0.75) — they are intentionally faster for a button press. Add `pressSpringResponse` and `pressSpringDamping` tokens to disambiguate.
- `DarkGlassIconButton` visual size is 36 × 36 pt but tap target must be 44 × 44 pt. Use `.frame(minWidth: 44, minHeight: 44)` on the `Button` wrapper, not on the visual capsule. The visual capsule stays 36 × 36 pt via an inner fixed frame.
- The confirm role's icon tint is `BeoColor.accent` (see naming conflict below). The cancel role uses `Color.red` (system adaptive red), NOT a hex value — this ensures it adapts correctly if Apple changes the system red in a future iOS release.
- Do not wrap multiple `DarkGlassButton` instances in a `GlassEffectContainer`. `GlassEffectContainer` causes adjacent glass surfaces to merge visually; the spec intends each button to be a separate pill.
- The haptic on the confirm button in `ConfirmationSheet` is `UINotificationFeedbackGenerator().notificationOccurred(.success)` (T-1109). T-2105 says "verify the `.medium` haptic from T-1108 still fires" — T-1108 is the sheet-appear `UIImpactFeedbackGenerator(style: .medium)` in `onAppear`, not the button tap haptic. Both must be preserved. The button tap haptic is at the `ConfirmationSheet` call site, not inside `DarkGlassButton` itself.

### Sheet dark mode (E-22)

- Add `.preferredColorScheme(.dark)` as the last modifier on the outermost view in `LanguagePickerSheet.body` and `ConfirmationSheet.body`, after `.frame(maxWidth: .infinity)` and before any presentation modifiers. Placement relative to `.presentationDetents` does not matter, but placing it last on the body root is the idiomatic convention.
- `LanguagePickerSheet` already calls `UIAccessibility.post(notification: .announcement, argument:)` in `onAppear`. This is a VoiceOver announcement, not contrast detection — it is not a `UIAccessibility.isContrastEnabled` call site and must NOT be removed by T-2204.
- Contrast reactive borders: `@Environment(\.colorSchemeContrast) private var contrast`. When `contrast == .increased`, set border line width to 1.0 and colour to `BeoColor.muted` (see naming conflict below). The shape and all other tokens remain unchanged.

## Conflicts

The following conflicts between the v1.1 spec and the current codebase require resolution before or during implementation. None are blockers to starting work, but each must be resolved before the relevant task closes.

### Conflict 1 — `BeoColor` property names do not match spec references (blocks T-2102, T-2205, T-2206)

The spec requires `DarkGlassButton` to reference `BeoColor.labelPrimary` and `BeoColor.labelSecondary`. These properties do not exist in `iOS/Voxio/DesignSystem/BeoColor.swift`. The current names are `BeoColor.text` (maps to `LabelPrimary` asset) and `BeoColor.muted` (maps to `LabelSecondary` asset).

**Resolution options:**
- Add `static let labelPrimary = BeoColor.text` and `static let labelSecondary = BeoColor.muted` aliases to `BeoColor`.
- Or rename `text` → `labelPrimary` and `muted` → `labelSecondary` and update all call sites.
- Either is acceptable. The rename is cleaner but touches more files. The alias is safer and non-breaking.

Do not leave `DarkGlassButton` referencing a name that does not compile.

### Conflict 2 — Design spec §Button Style prose conflicts with spec Technical Context on glass API (informational, no code impact)

The design spec (`design-spec-bo-voice-control.md`) §Button Style prose says buttons must "use `.ultraThinMaterial` with a `Color.black.opacity(0.45)` overlay". The design spec §Design Tokens Reference and the functional spec `VoxioSpecification-1.1.md` §Technical Context both resolve to the native iOS 26 `.glassEffect(.regular.tint(.black.opacity(0.45)).interactive(), in: Capsule())` API.

The functional spec Technical Context table is authoritative. Use the native iOS 26 `.glassEffect` API. The design spec prose is legacy wording from a pre-iOS-26 draft. No code change required — this is an informational flag for the design team to update the design spec prose.

### Conflict 3 — Button shape change: `RoundedRectangle(cornerRadius: 12)` → `Capsule()` (visible design change, verify against reference image)

All existing button surfaces in `ConfirmationSheet` and `LanguagePickerSheet` use `RoundedRectangle(cornerRadius: 12)`. The v1.1 `DarkGlassButton` uses `Capsule()`. On a standard 375 pt width with 24 pt horizontal padding, a full-width button is approximately 327 pt wide. At 10 pt vertical padding + 15 pt text, the button height is approximately 44–48 pt. A `Capsule()` at that aspect ratio produces a corner radius of ~22–24 pt, noticeably more rounded than `cornerRadius: 12`.

This is a deliberate design change specified by v1.1, but it must be visually verified against `ButtonLookAndFeel.png` before the E-23 snapshot tests are written, to ensure the reference image was generated at the same dimensions.

### Conflict 4 — `ConfirmationSheet` confirmation haptic is `.success` notification, not `.medium` impact (spec wording ambiguity)

T-2105 says "verify the existing `.medium` haptic from T-1108 still fires". T-1108 is the sheet-appear `UIImpactFeedbackGenerator(style: .medium)` in `ConfirmationSheet.onAppear`. The confirm button tap uses `UINotificationFeedbackGenerator().notificationOccurred(.success)` (T-1109) at the `ConfirmationSheet` call site — a separate, different haptic.

Both haptics must be preserved. The `.medium` impact fires on sheet appear; the `.success` notification fires on confirm button tap. The `DarkGlassButton` component itself must NOT fire any haptic — haptics remain the responsibility of the call site.

### Conflict 5 — `HintCardView` dismiss button uses `Radius.sheet` (16 pt), not `Capsule()` (informational)

The current `HintCardView` dismiss button uses `RoundedRectangle(cornerRadius: Radius.sheet)` (16 pt corner radius). T-2109 specifies replacing it with `DarkGlassButton(label: dismissLabel, role: .default, action: dismissHint)`, which uses `Capsule()`. This is the same shape change as Conflict 3 and is expected by the spec. The hint card itself remains `RoundedRectangle(cornerRadius: Radius.card)` — only the button inside it changes shape.

---

## Summary Verdict

**PROCEED.** No iOS platform constraint violations exist. The codebase already uses `.glassEffect`, targets iOS 26, and has `WindowGroup.preferredColorScheme(.dark)` in place. All five conflicts are resolvable during implementation without spec changes. Conflict 1 (BeoColor naming) is the only conflict that will cause a compile error if unresolved — it must be addressed before T-2102 closes.

Recommended first action for the implementer: resolve Conflict 1 (add `labelPrimary` and `labelSecondary` to `BeoColor`) before building `DarkGlassButton`, so token references compile from the first commit.
