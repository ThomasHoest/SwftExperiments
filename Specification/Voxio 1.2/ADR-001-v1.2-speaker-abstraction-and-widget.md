# ADR-001 — Voxio v1.2: Speaker Abstraction, Group Model, and Widget

**Status:** PROCEED  
**Date:** 2026-05-01  
**Author:** ARCHITECT agent (voxio-1.2 team)  
**Applies to:** iOS platform only (`iOS/Voxio/`)  
**References:** VoxioSpecification-1.2.md (v1.2.2), epics-and-tasks-voxio-1.2.md (v1.2.3), research-findings-voxio-1.2.md, design-spec-widget-voxio-1.2.md, design-spec-group-ui-voxio-1.2.md, api-spec-beonetremote.md, ADR-001-v1.1-visual-layer.md, ADR-002-v1.1-parsing-confirmation-trigger.md, CLAUDE.md

## Context

Voxio v1.2 adds three workstreams to the v1.1 codebase: (E-28/E-27) BNR speaker support via a shared protocol abstraction and a new `BNRClient`/`BNREvents` pair; (E-29/E-30/E-31) a WidgetKit home-screen widget, a Control Widget, and Siri `AppShortcutsProvider` integration; and (E-32) a `Group` model for multiroom sessions with voice join/leave commands. The v1.1 codebase (`Speaker`, `MozartClient`, `MozartEvents`, `MdnsDiscovery`, `HomeView`) was built for a single concrete API pair with no protocol boundary. This ADR validates the v1.2 specification against that baseline, identifies conflicts and platform constraint risks, and records the architectural decisions.

**Codebase state at the start of v1.2 planning:**

- `Speaker` holds `let client: MozartClient` and `let events: MozartEvents` directly (concrete references, no protocol).
- `MozartEvents` delivers events via `var onEvent: ((BeoEvent) -> Void)?` — a callback, not an `AsyncStream`.
- `MdnsDiscovery` browses `_bangolufsen._tcp` only, publishes `@Published var speakers: [Speaker]`, and is wrapped by a `SpeakerRegistry` layer referenced by `HomeView` via `@StateObject`.
- `HomeView` observes `registry.speakers` (a `[Speaker]` array from `SpeakerRegistry`) and catches errors typed as `MozartError` in its `perform()` helper.
- `ConfirmationCoordinator.startCountdown(action:readBack:onResolved:)` has a fixed 3-second duration (not configurable).
- `BeoColor.separator` is already declared: `static let separator = Color("BeoSeparator")` at line 11 of `BeoColor.swift`.

## Decision

The v1.2 architecture is adopted as specified, subject to the five required spec amendments listed below. The decisions recorded here are structurally sound. The platform constraints for widget, control widget, and Siri integration are satisfied by the iOS 26 deployment target. Implementation must not begin on E-27 (Speaker refactor), E-32 (join/leave dispatch), or E-30 (widget shared container) until the five amendments are resolved.

### Decision 1 — Protocol abstraction: `any SpeakerClient` existential is sufficient

`Speaker` holds `any SpeakerClient` and `any SpeakerEventSource` (Swift 5.7+ open existentials). The use sites — `Speaker.play()`, `Speaker.setVolume(_:)`, and all other delegation calls — require no associated types or generic constraints, so the existential is the correct choice over generics (`some SpeakerClient`). Protocol witnesses are dispatched via existential dispatch at runtime; given the low call frequency of speaker API methods (human-initiated commands and periodic events), the existential overhead is negligible.

`@Observable @MainActor Speaker` composes correctly with existential protocol-typed properties: changes to observable state properties (`name`, `state`, `volume`, etc.) still trigger SwiftUI re-renders as expected. The `@MainActor` isolation is preserved by the existing `Task { @MainActor in self?.handleEvent(event) }` pattern.

### Decision 2 — `AsyncStream` bridge for `MozartEvents`

The retroactive `SpeakerEventSource` conformance for `MozartEvents` wraps the existing `onEvent` callback in an `AsyncStream<SpeakerEvent>`. The bridge is sound but carries one risk: `onEvent` is not thread-safe today — the WebSocket receive callback fires on an arbitrary queue. The bridge extension must ensure `continuation.yield` is called on `@MainActor`. T-2704 must document this explicitly.

### Decision 3 — E-28 before E-27 implementation order

Implementing `BNRClient` and `BNREvents` as standalone concrete types before defining the `SpeakerClient`/`SpeakerEventSource` protocols is architecturally correct. The most divergent BNR constraints — broadcast-only join, absence of a peers endpoint, press+release double-POST, 0–`range.maximum` volume normalisation — would not be visible from the Mozart-only codebase. The E-28-first order prevents over-fitting the protocol surface to Mozart's API shape. Adopted.

### Decision 4 — Group model as a new top-level observable entity

`Group` as `@Observable @MainActor final class` with `var members: [Speaker]` and `var hostSpeaker: Speaker` is architecturally sound on iOS 26. `@Observable` nested observation (changes to `hostSpeaker.playbackState` propagating to views reading `group.playbackState`) is confirmed behavior for iOS 17+. A group-of-1 rendering `SpeakerCard(speaker: group.hostSpeaker)` directly requires no new view types for the single-speaker case, eliminating regression risk.

**The Group model is explicitly cross-platform.** A single Group may contain any mix of Mozart and BNR speakers. Platform-specific join/leave logic is fully encapsulated within each client's `join(peer:)` and `leave()` implementations.

### Decision 5 — `SpeakerDiscoveryService` settle window and startup reconstruction

The 500 ms settle window before `reconstructGroups()` is appropriate for local mDNS discovery. The union-find approach on Mozart peer JIDs is sound. BNR reconstruction via `multiroom` field heuristics is accepted as best-effort per Open Question 16. The spec's graceful degradation (timeout → group-of-1, no toast) is correct.

### Decision 6 — Widget: App Groups + `AudioPlaybackIntent`

App Groups (`group.T-Creative.Voxio`) backed by `UserDefaults(suiteName:)` is the correct and only supported mechanism for main app-to-widget-extension state sharing on iOS 26. No newer alternative exists. `AudioPlaybackIntent.perform()` routing to the main app process is the correct mechanism for widget button taps that require LAN network calls. The spec's requirement that the app must be running in the background is correct and accurately documented.

`WidgetCenter.shared.reloadAllTimelines()` called on every Speaker event is within the WidgetKit budget. However, with multiple active speakers generating frequent events, a **500 ms debounce** on the write+reload path is recommended to avoid unnecessary widget re-renders (see OQ-C). Not a blocker, flagged for T-2731.

### Decision 7 — Control Widget API

`ControlWidgetButton` and `ControlWidgetToggle` with `AppIntentControlConfiguration` are the correct iOS 18+ APIs. iOS 26 makes them available on macOS and watchOS automatically — no additional implementation required.

### Decision 8 — Join voice command: `join(peer:)` protocol asymmetry

The `join(peer:)` protocol method has inverted call-site semantics between Mozart and BNR:

- **Mozart→Mozart:** `join(peer: A.identifier)` is called on **B's client** (target). B internally calls `beolinkExpand(jid: A.jid)`.
- **BNR→Any:** `join(peer: target.identifier)` is called on **A's client** (source). A internally calls `POST /BeoZone/Zone/Device/OneWayJoin` (broadcast; peer arg is informational only).

This asymmetry is handled correctly in T-2757/T-2758 but the `SpeakerClient` protocol doc comment must make the caller-direction semantics explicit (Required Amendment 4).

### Decision 9 — Leave voice command: immediate execution

`leaveSpeaker` executing immediately with no countdown is correct per the functional spec. Leave restores standalone playback and is recoverable by a single join command. The design-spec-group-ui-voxio-1.2.md §4.1 specifies a 1-second voice-leave countdown — this directly contradicts the functional spec. **Conflict 2 must be resolved before T-2754 begins.**

### Decision 10 — BNR 501 soft-warning

Treating HTTP 501 on BNR write operations as a soft warning (log at INFO, do not throw) is consistent with documented community implementations and is sound. The `BNRClient` implementation must log before returning — never silently ignore.

## Options Considered

### Speaker abstraction mechanism

| Option | Verdict |
|---|---|
| **A (chosen): `protocol SpeakerClient` + `any` existentials** | Allows retroactive conformances with no logic changes. Compatible with `@Observable @MainActor`. No type-erasure boilerplate. |
| B (rejected): Combine `AnyPublisher<SpeakerEvent, Never>` | Would require replacing `@Observable` with `ObservableObject`/`@Published`. Zero Combine usage in codebase; introduces mixed concurrency model with no benefit. |
| C (rejected): Base class | Swift single-inheritance + `@MainActor @Observable` stack makes this fragile. |
| D (considered): `some SpeakerClient` opaque return | Rejected at the `Speaker` stored-property use site — `some` is a compile-time single-type constraint and cannot represent a property that may be either `MozartClient` or `BNRClient` at runtime. |

### BNR event delivery

| Option | Verdict |
|---|---|
| **A (chosen): `AsyncStream<SpeakerEvent>` with long-poll `Task` loop** | Matches BNR HTTP long-poll model exactly. Exponential backoff on network error. Stream termination on `Task` cancellation. |
| B (rejected): WebSocket for BNR | BNR does not expose a WebSocket endpoint. |
| C (rejected): Polling REST | Timer-based poll of `GET /BeoZone/Zone/ActiveSources` introduces unnecessary device and speaker load. Long-poll provides push semantics. |

### Group top-level entity

| Option | Verdict |
|---|---|
| **A (chosen): `Group` as new `@Observable @MainActor` class, replaces `[Speaker]` in UI** | Clean encapsulation of peer-graph reconstruction, cross-platform membership, and host promotion. Group-of-1 is structurally identical to group-of-N from the view layer. |
| B (rejected): Augment `Speaker` with `group: Group?` backlink | Creates circular reference graph. Group dissolution and host promotion logic distributed across Speaker instances. |
| C (rejected): `[Speaker]` with grouping metadata in a parallel dictionary | Splits group state across two structures. Error-prone and inconsistent with the `@Observable` reactive model. |

### Widget state sharing

| Option | Verdict |
|---|---|
| **A (chosen): App Groups `UserDefaults(suiteName:)`** | Established iOS pattern. Synchronous reads/writes. No new framework dependency. |
| B (rejected): `SwiftData` shared container | Same App Groups entitlement required. Overkill for a flat key-value model. |
| C (rejected): CloudKit shared container | Introduces cloud dependency. Violates local-network-only privacy requirement. |

## Consequences

### Positive

- `MozartClient`/`MozartEvents` acquire protocol conformances with zero logic changes, verified by T-2710 regression pass.
- `Speaker`'s call sites are syntactically unchanged after protocol refactor.
- Group-of-1 renders identically to v1.1 speaker card — no regression for single-speaker users.
- `BNRClient`/`BNREvents` are self-contained with no coupling to Mozart implementation details.
- `AsyncStream<SpeakerEvent>` gives `Speaker` a uniform event loop regardless of transport (WebSocket or long-poll).
- Protocol mocks make `Speaker`, `Group`, and `SpeakerDiscoveryService` fully unit-testable without network access.

### Negative

- The `MozartEvents` callback-to-`AsyncStream` bridge (T-2704) is a non-trivial concurrency boundary. Incorrect `@MainActor` isolation on `continuation.yield` introduces a data race.
- `SpeakerDiscoveryService`'s 500 ms settle window is a heuristic. On slow mDNS networks, groups may be reconstructed incorrectly on first launch. Self-healing on next launch is the mitigation.
- `AudioPlaybackIntent.perform()` requiring the app to be running is a persistent UX limitation. Users who routinely force-quit apps will encounter the fallback state frequently.
- `WidgetCenter.shared.reloadAllTimelines()` on every speaker event without a debounce may consume the WidgetKit refresh budget during high-activity multi-speaker playback sessions.
- `DesignTokens.swift` and `BeoColor.swift` added to the widget extension target creates dual-target file ownership — build system drift risk if tokens are added to only one target.
- `Group.id` recomputation on membership change means the App Groups shared container must be updated on join/leave events, not just on speaker state events.

## Conflicts with Existing Patterns

### Conflict 1 — `HomeView` uses `SpeakerRegistry`, not `MdnsDiscovery` directly (Critical — blocks T-2747)

`HomeView.swift` observes `@StateObject private var registry = SpeakerRegistry()` and accesses `registry.speakers`. The spec and T-2747 describe refactoring `HomeView` to bind to `[Group]` from `SpeakerDiscoveryService` but do not mention `SpeakerRegistry`. `SpeakerRegistry` also owns `registry.favorites` and `registry.resolve(words:)` — both used by the voice pipeline. `SpeakerDiscoveryService` replaces `SpeakerRegistry`; favorites migrate to `FavoritesService`, speaker resolution migrates to `SpeakerDiscoveryService.resolve(speakerName:)`. T-2747 and T-2765 address this migration.

**→ Required Amendment 1. RESOLVED in v1.2.3 (T-2747 updated, T-2765 added).**

### Conflict 2 — Voice-leave confirmation policy contradiction (Critical — blocks T-2754)

`VoxioSpecification-1.2.md` §Technical Context says "Leave is immediate — no countdown required." `design-spec-group-ui-voxio-1.2.md` §4.1 says voice-initiated leave uses a 1-second countdown. These contradict each other. Additionally, `ConfirmationCoordinator.startCountdown` has a hardcoded 3-second duration (ADR-002 Decision 2) — a 1-second countdown would require a new `duration: TimeInterval` parameter.

**→ Required Amendment 2. RESOLVED in v1.2.3 (design spec §4.1 rewritten; T-2754 updated; voice-leave is immediate, ConfirmationCoordinator unchanged).**

### Conflict 3 — `HomeView.perform()` catches `MozartError`; will miss `SpeakerError` after refactor (Critical — blocks T-2705)

`HomeView.perform()` at line ~442 catches `MozartError`. After T-2705 refactors `Speaker` to dispatch through `any SpeakerClient`, BNR commands will throw `SpeakerError` (the new unified error type). BNR timeout errors will not map to `.apiTimeout`; they will fall through to the generic catch block. All `MozartError`-typed catch clauses in `iOS/Voxio/Features/` must be audited and updated.

**→ Required Amendment 3. RESOLVED in v1.2.3 (T-2766 adds SpeakerError.swift; T-2703 wraps MozartError via SpeakerError.from(); T-2705 audits all catch clauses; T-2711 throws SpeakerError directly).**

### Conflict 4 — `BeoColor.separator` already exists (Non-blocking, informational)

`BeoColor.swift` line 11 already declares `static let separator = Color("BeoSeparator")`. T-2730 as written would produce a duplicate declaration compile error.

**→ Required Amendment 5. RESOLVED in v1.2.3 (T-2730 updated to explicitly prohibit re-adding the existing declaration).**

### Conflict 5 — `Speaker.isInitializing` shimmer state does not exist in v1.1 (Moderate — informational)

`design-spec-group-ui-voxio-1.2.md` §5.1 references `Speaker.isInitializing` behaviour for the startup loading shimmer. No such property exists in `Speaker.swift`. T-2747 must either add `isInitializing: Bool` to `Speaker` or document that default-state rendering (blank name, `.unknown` playback state) is the implemented stand-in.

## Platform Constraint Violations

No hard platform constraint violations. All required APIs are available on the iOS 26 deployment target:

| API | Minimum iOS | Status |
|---|---|---|
| `protocol` / `any` existential | iOS 16 (Swift 5.7) | ✓ Satisfied |
| `AsyncStream` | iOS 15 (Swift 5.5) | ✓ Satisfied |
| `WidgetKit` interactive `Button(intent:)` | iOS 17 | ✓ Satisfied |
| `ControlWidgetButton` / `ControlWidgetToggle` | iOS 18 | ✓ Satisfied |
| `AppShortcutsProvider` | iOS 16.4 | ✓ Satisfied |
| `AudioPlaybackIntent` | iOS 17 | ✓ Satisfied |
| `.glassEffect` widget rendering | iOS 26 | ✓ Satisfied |
| App Groups entitlement | All iOS | ✓ Provisioning update required (T-2728, P0) |
| `_beoremote._tcp` in `NSBonjourServices` | All iOS | ✓ Info.plist update required (T-2707) |
| `NSAllowsLocalNetworking` (plain HTTP, port 8080) | All iOS | ✓ Already present in Info.plist |

**Flagged risks (not hard violations):**

- **Widget refresh budget (MEDIUM):** `reloadAllTimelines()` on every speaker event without a debounce risks exhausting the budget during high-activity multi-speaker sessions. Mitigate with ≥500 ms debounce in T-2731.
- **`AudioPlaybackIntent` background routing (LOW-MEDIUM):** Users who force-quit apps will encounter widget fallback state more often than expected. Product communication concern, not a platform violation.
- **BNR long-poll background suspension (LOW):** `Task` is suspended (not cancelled) on background entry. `URLSession` resumes normally on foreground return. Exponential backoff handles dropped connections. T-2717 should document this with a code comment.
